# spec-draft — proposed STAC extensions for searchable gazetteers

**Status: draft for discussion.** See
[issue #1](https://github.com/cholmes/cng-map-widgets/issues/1). Nothing here is
published, and the schema URLs are `example.org` placeholders until there is a
home for them.

This directory holds worked examples of a proposal to replace this repo's
bespoke `cnmw-index/1.0` manifest with two STAC extensions.

## The two extensions

**`gazetteer`** — lets a client search names and get a bbox. One sorted names
index parquet, its column contract, and the normalization/sort guarantee.

**`gazetteer-boundaries`** — upgrades that bbox to a polygon. Per-level
boundary assets, their join columns, and the `geometry_ref` fast path.

The split matters because `gazetteer` alone is already a shippable product: a
search box that resolves a place and flies the map to its bbox, with no geometry
fetched. It also means a publisher with existing boundary files can adopt the
index half without producing anything new.

## Examples

### [`geoboundaries-cgaz-collection.json`](examples/geoboundaries-cgaz-collection.json)

**Both extensions, and every value is real** — generated by transforming the
live manifest at
`data.source.coop/portolan-mirrors/geoboundaries-catalog/names/index.json`
(2026-11-17), with the `table:columns` entries read from the published parquet's
actual schema. Nothing is invented. Worth looking at for three things:

- `gazetteer:feature_id_column: null` on the ADM0 boundary asset. Legal and
  meaningful: CGAZ ADM0 has no ID column at all, so resolution joins on
  `gazetteer:index_key_column: "country"` against `shapeGroup` instead. Any
  schema for this extension has to permit an explicit null.
- The published schema **matches** the documented contract: `bbox` is a struct
  with `xmin`/`ymin`/`xmax`/`ymax` and is declared as a GeoParquet 1.1
  `covering` in the file's `geo` metadata, and `geometry_ref` is a struct with
  `file`/`row_group`/`row`. (An earlier draft of this file claimed these were
  flat columns. That was wrong — a leaf-only schema query had stripped the
  struct parent from the path.) The only genuine gaps are small: the index
  carries an undocumented `geometry` column holding an inline WKB label point,
  plus `shape_type` and `name_dupes` as publisher extras. `source` and
  `parent_name` are absent, but AGENTS.md already documents those as
  defaultable and read-when-present respectively.

- `attribution[]` with its `share_alike` boolean collapses into STAC `license`
  (an SPDX id) plus `providers[]`, which removes the casing hazard where
  `share_alike` and `shareAlike` disagreed and checking one silently
  under-reported ODbL obligations.

### [`fieldmaps-index-only-collection.json`](examples/fieldmaps-index-only-collection.json)

**`gazetteer` alone — illustrative, not published.** What adoption would look
like for a catalog that already has boundary files. Row counts and source column
names are taken from the real published `fieldmaps/subnational/global` layers;
the index asset is hypothetical.

The point of this example is how little it asks. Every index column maps
directly to a column that catalog already publishes — `adm2_name`,
`adm0_name`, `area_sqkm`, `iso3`, `src_lic` — because parent and country names
are already denormalized onto every row upstream, so no join is needed. The
name columns are about 16.5 MB across ADM1-ADM4 against roughly 5.2 GB of
geometry, so extracting them is close to free.

Note what is deliberately *not* tagged: the existing ADM2 polygon file is listed
with `roles: ["data"]`, not `gazetteer-boundaries`. Tagging it would pull in the
second extension and a join column. Keeping it untagged is the whole argument
for splitting the two.

## What a JSON Schema cannot check

The requirement that makes the format work is that rows ascend by `name_norm`
compared **byte-wise on its UTF-8 encoding**, produced by one specific
normalization (NFD → strip combining marks → lowercase → keep
`[\p{L}\p{N} '-]` → collapse whitespace → trim).

No JSON Schema expresses that, and no STAC validator will check it. Schema
conformance is **necessary but not sufficient** — a catalog that validates can
still break every client. A conformance checker that reads the parquet and
verifies the sort is part of the proposal, not an optional extra.
